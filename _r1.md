### 1.2 Loop de frame

```csharp
void Update()
{
    if (!isPaused)
    {
        float maxDeltaTime = maxTimestepFPS > 0 ? 1 / maxTimestepFPS : float.PositiveInfinity; // If framerate dips too low, run the simulation slower than real-time
        float dt = Mathf.Min(Time.deltaTime * timeScale, maxDeltaTime);
        RunSimulationFrame(dt);
    }
    ...
}

void RunSimulationFrame(float frameTime)
{
    float timeStep = frameTime / iterationsPerFrame;

    UpdateSettings(timeStep);

    for (int i = 0; i < iterationsPerFrame; i++)
    {
        RunSimulationStep();
        SimulationStepCompleted?.Invoke();
    }
}

void RunSimulationStep()
{
    ComputeHelper.Dispatch(compute, numParticles, kernelIndex: externalForcesKernel);

    RunSpatial();

    ComputeHelper.Dispatch(compute, numParticles, kernelIndex: densityKernel);
    ComputeHelper.Dispatch(compute, numParticles, kernelIndex: pressureKernel);
    ComputeHelper.Dispatch(compute, numParticles, kernelIndex: viscosityKernel);
    ComputeHelper.Dispatch(compute, numParticles, kernelIndex: updatePositionKernel);
}

void RunSpatial()
{
    ComputeHelper.Dispatch(compute, numParticles, kernelIndex: spatialHashKernel);
    spatialHash.Run();

    ComputeHelper.Dispatch(compute, numParticles, kernelIndex: reorderKernel);
    ComputeHelper.Dispatch(compute, numParticles, kernelIndex: copybackKernel);
}
```

Pontos de fato:
- `UpdateSettings(timeStep)` é chamado **uma vez por frame**, não por sub-step (o `deltaTime` do shader é o `timeStep` do sub-step).
- `Init()` faz `Time.fixedDeltaTime = 1/60f` mas a simulação roda em `Update()`, não em `FixedUpdate()`. Ou seja: **não há delta time fixo real**; há apenas o clamp `maxTimestepFPS = 60` → `dt ≤ 16.67 ms`, e 3 sub-steps ⇒ `dt_sub ≤ 5.56 ms`.
- O 3D adiciona `if (viscosityStrength != 0)` antes do dispatch de viscosidade (`FluidSim.cs`, `RunSimulationStep`), otimização que o 2D **não** tem.

## 2. Algoritmo SPH — fórmulas e constantes

### 2.1 Kernels de suavização 2D (`FluidMaths2D.hlsl`, arquivo inteiro)

```hlsl
const float Poly6ScalingFactor;
const float SpikyPow3ScalingFactor;
const float SpikyPow2ScalingFactor;
const float SpikyPow3DerivativeScalingFactor;
const float SpikyPow2DerivativeScalingFactor;

float SmoothingKernelPoly6(float dst, float radius)
{
	if (dst < radius)
	{
		float v = radius * radius - dst * dst;
		return v * v * v * Poly6ScalingFactor;
	}
	return 0;
}

float SpikyKernelPow3(float dst, float radius)
{
	if (dst < radius)
	{
		float v = radius - dst;
		return v * v * v * SpikyPow3ScalingFactor;
	}
	return 0;
}

float SpikyKernelPow2(float dst, float radius)
{
	if (dst < radius)
	{
		float v = radius - dst;
		return v * v * SpikyPow2ScalingFactor;
	}
	return 0;
}

float DerivativeSpikyPow3(float dst, float radius)
{
	if (dst <= radius)
	{
		float v = radius - dst;
		return -v * v * SpikyPow3DerivativeScalingFactor;
	}
	return 0;
}

float DerivativeSpikyPow2(float dst, float radius)
{
	if (dst <= radius)
	{
		float v = radius - dst;
		return -v * SpikyPow2DerivativeScalingFactor;
	}
	return 0;
}
```

Constantes calculadas no host (`FluidSim2D.cs`, `UpdateSettings`):

```csharp
compute.SetFloat("Poly6ScalingFactor", 4 / (Mathf.PI * Mathf.Pow(smoothingRadius, 8)));
compute.SetFloat("SpikyPow3ScalingFactor", 10 / (Mathf.PI * Mathf.Pow(smoothingRadius, 5)));
compute.SetFloat("SpikyPow2ScalingFactor", 6 / (Mathf.PI * Mathf.Pow(smoothingRadius, 4)));
compute.SetFloat("SpikyPow3DerivativeScalingFactor", 30 / (Mathf.Pow(smoothingRadius, 5) * Mathf.PI));
compute.SetFloat("SpikyPow2DerivativeScalingFactor", 12 / (Mathf.Pow(smoothingRadius, 4) * Mathf.PI));
```

**Tabela pronta (2D, $h$ = `smoothingRadius`, $q = h - d$):**

| Kernel | Fórmula | Constante | Verificação |
|---|---|---|---|
| Poly6 | $W = C\,(h^2-d^2)^3$ | $C = \dfrac{4}{\pi h^8}$ | $\int_0^h (h^2-d^2)^3\,2\pi d\,\mathrm{d}d = \pi h^8/4$ ✔ |
| Spiky² (densidade) | $W = C\,q^2$ | $C = \dfrac{6}{\pi h^4}$ | $2\pi\int_0^h q^2 d\,\mathrm{d}d = \pi h^4/6$ ✔ |
| Spiky³ (near-densidade) | $W = C\,q^3$ | $C = \dfrac{10}{\pi h^5}$ | $2\pi\int_0^h q^3 d\,\mathrm{d}d = \pi h^5/10$ ✔ |
| $\partial_d$ Spiky² | $W' = -C'\,q$ | $C' = \dfrac{12}{\pi h^4} = 2C_{\text{Spiky}^2}$ | derivada exata ✔ |
| $\partial_d$ Spiky³ | $W' = -C'\,q^2$ | $C' = \dfrac{30}{\pi h^5} = 3C_{\text{Spiky}^3}$ | derivada exata ✔ |

### 2.3 Mapeamento kernel→uso (2D, `FluidSim2D.compute`)

```hlsl
float DensityKernel(float dst, float radius)      { return SpikyKernelPow2(dst, radius); }
float NearDensityKernel(float dst, float radius)  { return SpikyKernelPow3(dst, radius); }
float DensityDerivative(float dst, float radius)  { return DerivativeSpikyPow2(dst, radius); }
float NearDensityDerivative(float dst, float radius) { return DerivativeSpikyPow3(dst, radius); }
float ViscosityKernel(float dst, float radius)    { return SmoothingKernelPoly6(dst, smoothingRadius); }
```

> 🐛 Note: `ViscosityKernel` **ignora o parâmetro `radius`** e usa o uniform global `smoothingRadius`. Inofensivo aqui (sempre chamado com o mesmo valor), mas não replique.

**Não existe termo de massa**: massa é implicitamente 1 e a densidade é adimensional (daí `targetDensity` valer 55 em 2D e 630 em 3D).

### 2.4 Densidade

```hlsl
float2 CalculateDensity(float2 pos)
{
	int2 originCell = GetCell2D(pos, smoothingRadius);
	float sqrRadius = smoothingRadius * smoothingRadius;
	float density = 0;
	float nearDensity = 0;

	// Neighbour search
	for (int i = 0; i < 9; i++)
	{
		uint hash = HashCell2D(originCell + offsets2D[i]);
		uint key = KeyFromHash(hash, numParticles);
		uint currIndex = SpatialOffsets[key];

		while (currIndex < numParticles)
		{
			uint neighbourIndex = currIndex;
			currIndex ++;
			
			uint neighbourKey = SpatialKeys[neighbourIndex];
			// Exit if no longer looking at correct bin
			if (neighbourKey != key) break;

			float2 neighbourPos = PredictedPositions[neighbourIndex];
			float2 offsetToNeighbour = neighbourPos - pos;
			float sqrDstToNeighbour = dot(offsetToNeighbour, offsetToNeighbour);

			// Skip if not within radius
			if (sqrDstToNeighbour > sqrRadius) continue;

			// Calculate density and near density
			float dst = sqrt(sqrDstToNeighbour);
			density += DensityKernel(dst, smoothingRadius);
			nearDensity += NearDensityKernel(dst, smoothingRadius);
		}
	}

	return float2(density, nearDensity);
}
```

A própria partícula **é** incluída na soma de densidade (não há `if (neighbourIndex == id.x) continue;` aqui) — só é excluída em pressão e viscosidade. Isso garante $\rho_i \ge W(0)$, evitando divisão por zero.

### 2.5 Equação de estado (dupla: pressão + near-pressão)

```hlsl
float PressureFromDensity(float density)
{
	return (density - targetDensity) * pressureMultiplier;
}

float NearPressureFromDensity(float nearDensity)
{
	return nearPressureMultiplier * nearDensity;
}
```

$$P_i = k\,(\rho_i - \rho_0), \qquad P^{\text{near}}_i = k_{\text{near}}\,\rho^{\text{near}}_i$$

É a formulação de **Clavet et al. 2005** ("double density relaxation"): a near-pressure é sempre repulsiva (nunca negativa), o que impede o clustering/colapso que a EOS linear pura provoca quando $\rho < \rho_0$. Sem ela, com `pressureMultiplier` alto, o fluido explode/agrupa.

### 2.6 Força de pressão (simétrica)

```hlsl
			float sharedPressure = (pressure + neighbourPressure) * 0.5;
			float sharedNearPressure = (nearPressure + neighbourNearPressure) * 0.5;

			pressureForce += dirToNeighbour * DensityDerivative(dst, smoothingRadius) * sharedPressure / neighbourDensity;

```

$$\mathbf{a}_i = \frac{1}{\rho_i}\sum_{j \ne i} \hat{\mathbf{r}}_{ij}\left[\frac{\bar P_{ij}\,W'_{\text{Spiky}^2}(d)}{\rho_j} + \frac{\bar P^{\text{near}}_{ij}\,W'_{\text{Spiky}^3}(d)}{\rho^{\text{near}}_j}\right]$$

com $\hat{\mathbf{r}}_{ij} = (\mathbf{x}_j-\mathbf{x}_i)/d$ e $\bar P_{ij}=(P_i+P_j)/2$. O sinal negativo está embutido nas derivadas (`return -v * ...`).

Degenerescência tratada:
```hlsl

```

### 2.7 Viscosidade (XSPH-like com Poly6)

```hlsl
			float dst = sqrt(sqrDstToNeighbour);
			float2 neighbourVelocity = Velocities[neighbourIndex];
			viscosityForce += (neighbourVelocity - velocity) * ViscosityKernel(dst, smoothingRadius);
```

$$\mathbf{v}_i \mathrel{+}= \Delta t\,\nu \sum_{j\ne i}(\mathbf{v}_j-\mathbf{v}_i)\,W_{\text{Poly6}}(d)$$

Sem divisão por densidade — é suavização de velocidade, não viscosidade física. **Estabilidade**: $\nu\,\Delta t\,\sum W$ deve ficar < 1, senão inverte velocidades. Com `viscosityStrength = 0.03` e $h=0.35$ é seguro.

### 2.8 Forças externas + predição

```hlsl
float2 ExternalForces(float2 pos, float2 velocity)
{
	// Gravity
	float2 gravityAccel = float2(0, gravity);
	
	// Input interactions modify gravity
	if (interactionInputStrength != 0) {
		float2 inputPointOffset = interactionInputPoint - pos;
		float sqrDst = dot(inputPointOffset, inputPointOffset);
		if (sqrDst < interactionInputRadius * interactionInputRadius)
		{
			float dst = sqrt(sqrDst);
			float edgeT = (dst / interactionInputRadius);
			float centreT = 1 - edgeT;
			float2 dirToCentre = inputPointOffset / dst;

			float gravityWeight = 1 - (centreT * saturate(interactionInputStrength / 10));
			float2 accel = gravityAccel * gravityWeight + dirToCentre * centreT * interactionInputStrength;
			accel -= velocity * centreT;
			return accel;
		}
	}

	return gravityAccel;
}
```

```hlsl
[numthreads(NumThreads,1,1)]
void ExternalForces(uint3 id : SV_DispatchThreadID)
{
	if (id.x >= numParticles) return;

	// External forces (gravity and input interaction)
	Velocities[id.x] += ExternalForces(Positions[id.x], Velocities[id.x]) * deltaTime;

	// Predict
	const float predictionFactor = 1 / 120.0;
	PredictedPositions[id.x] = Positions[id.x] + Velocities[id.x] * predictionFactor;
}
```

**Detalhe crítico e contraintuitivo**: a predição usa **constante fixa de `1/120` segundos**, *não* `deltaTime`. Isso desacopla o lookahead do timestep (mais estável quando o fps varia). O 3D é idêntico: `PredictedPositions[id.x] = Positions[id.x] + Velocities[id.x] * 1 / 120.0;`.

### 2.9 Integração

```hlsl
[numthreads(NumThreads, 1, 1)]
void UpdatePositions(uint3 id : SV_DispatchThreadID)
{
	if (id.x >= numParticles) return;

	Positions[id.x] += Velocities[id.x] * deltaTime;
	HandleCollisions(id.x);
}
```

Euler semi-implícito (symplectic Euler): a velocidade é atualizada em 3 estágios (gravidade → pressão → viscosidade) e só então a posição usa a velocidade já atualizada.

**Resumo do passo completo:**
1. $\mathbf v \mathrel{+}= \mathbf a_{\text{ext}}\Delta t$
2. $\tilde{\mathbf x} = \mathbf x + \mathbf v\cdot\frac{1}{120}$ (predição)
3. hash+sort+offsets+reorder sobre $\tilde{\mathbf x}$
4. $\rho, \rho^{\text{near}}$ em $\tilde{\mathbf x}$
5. $\mathbf v \mathrel{+}= \mathbf a_{P}\Delta t$
6. $\mathbf v \mathrel{+}= \nu(\ldots)\Delta t$
7. $\mathbf x \mathrel{+}= \mathbf v\Delta t$; colisões

## 3. Hash espacial e ordenação

### 3.1 Hash 2D (`Sim2D/Compute/SpatialHash.hlsl`, arquivo inteiro)

```hlsl
static const int2 offsets2D[9] =
{
	int2(-1, 1),
	int2(0, 1),
	int2(1, 1),
	int2(-1, 0),
	int2(0, 0),
	int2(1, 0),
	int2(-1, -1),
	int2(0, -1),
	int2(1, -1),
};

// Constants used for hashing
static const uint hashK1 = 15823;
static const uint hashK2 = 9737333;

// Convert floating point position into an integer cell coordinate
int2 GetCell2D(float2 position, float radius)
{
	return (int2)floor(position / radius);
}

// Hash cell coordinate to a single unsigned integer
uint HashCell2D(int2 cell)
{
	cell = (uint2)cell;
	uint a = cell.x * hashK1;
	uint b = cell.y * hashK2;
	return (a + b);
}

uint KeyFromHash(uint hash, uint tableSize)
{
	return hash % tableSize;
}
```

- **Tamanho de célula = `smoothingRadius`** exatamente ⇒ 3×3 = 9 células cobrem o suporte do kernel. Em 3D, 3×3×3 = 27.
- `tableSize == numParticles` (passado como `KeyFromHash(hash, numParticles)`), logo `SpatialOffsets` tem N entradas e há colisões de hash aceitas (partículas de células distintas podem cair no mesmo bin — o loop só compara `key`, não a célula, então **colisões causam vizinhos falsos**; é um erro tolerado por ser raro e visualmente inócuo).
- `%` por um N não potência de dois é uma divisão inteira por dispatch·9 — em Mali/Adreno isso é caro. `[INFERÊNCIA]` Use `tableSize` potência de 2 e `hash & (tableSize-1)`.

### 3.2 Hash 3D (`Simulation/Compute/SpatialHash3D.hlsl`)

```hlsl
static const uint hashK1 = 15823;
static const uint hashK2 = 9737333;
static const uint hashK3 = 440817757;
...
uint HashCell3D(int3 cell)
{
	const uint blockSize = 50;
	uint3 ucell = (uint3) (cell + blockSize / 2);

	uint3 localCell = ucell % blockSize;
	uint3 blockID = ucell / blockSize;
	uint blockHash = blockID.x * hashK1 + blockID.y * hashK2 + blockID.z * hashK3;
	return localCell.x + blockSize * (localCell.y + blockSize * localCell.z) + blockHash;
}
```

Hash híbrido: dentro de blocos de 50³ é **indexação linear** (vizinhos ficam com keys próximas ⇒ melhor localidade de cache), e entre blocos é hash multiplicativo. O comentário no arquivo é honesto: `// TODO: investigate better hashing functions`.

### 3.3 Não é bitonic sort — é **counting sort**

`Assets/Scripts/Helpers/GPU Sort/CountSort/Resources/CountSort.compute` (arquivo inteiro):

```hlsl
#pragma kernel ClearCounts
#pragma kernel CalculateCounts
#pragma kernel ScatterOutput
#pragma kernel CopyBack

RWStructuredBuffer<uint> InputItems;
RWStructuredBuffer<uint> InputKeys;
RWStructuredBuffer<uint> SortedItems;
RWStructuredBuffer<uint> SortedKeys;

RWStructuredBuffer<uint> Counts;
uint numInputs;

static const int GroupSize = 256;

[numthreads(GroupSize, 1, 1)]
void ClearCounts(uint3 id : SV_DispatchThreadID)
{
	if (id.x >= numInputs) return;

	Counts[id.x] = 0;
	InputItems[id.x] = id.x;
}

[numthreads(GroupSize, 1, 1)]
void CalculateCounts(uint3 id : SV_DispatchThreadID)
{
	if (id.x >= numInputs) return;

	uint key = InputKeys[id.x];
	InterlockedAdd(Counts[key], 1);
}

[numthreads(GroupSize, 1, 1)]
void ScatterOutput(uint3 id : SV_DispatchThreadID)
{
	if (id.x >= numInputs) return;

	uint key = InputKeys[id.x];

	uint sortedIndex;
	InterlockedAdd(Counts[key], 1, sortedIndex);

	SortedItems[sortedIndex] = InputItems[id.x];
	SortedKeys[sortedIndex] = key;
}

[numthreads(GroupSize, 1, 1)]
void CopyBack(uint3 id : SV_DispatchThreadID)
{
	if (id.x >= numInputs) return;

	InputItems[id.x] = SortedItems[id.x];
	InputKeys[id.x] = SortedKeys[id.x];
}
```

Pontos importantes:
- `ClearCounts` também **inicializa `InputItems[i] = i`** (a identidade que virará `SortedIndices`).
- `Counts` tem `maxValue+1` entradas. O host chama `gpuSort.Run(SpatialIndices, SpatialKeys, (uint)(SpatialKeys.count - 1))` ⇒ **`Counts` tem N entradas**.
- Complexidade $O(N)$, contra $O(N\log^2 N)$ do bitonic. É o motivo pelo qual escala para 410k partículas.
- Depende de `InterlockedAdd` em buffer (atomics em SSBO). Suportado em ES3.1, mas com **contenção alta**: todas as partículas de uma mesma célula batem no mesmo endereço.

### 3.4 Prefix scan (`ScanTest.compute`)

```hlsl
#pragma kernel BlockScan
#pragma kernel BlockCombine
// Parallel Prefix Sum (scan)
// https://www.eecs.umich.edu/courses/eecs570/hw/parprefix.pdf

static const uint GROUP_SIZE = 256;
static const uint ITEMS_PER_GROUP = 2 * GROUP_SIZE; // 2 items processed per thread

RWStructuredBuffer<uint> Elements;
RWStructuredBuffer<uint> GroupSums;

```

Scan exclusivo de Blelloch clássico: up-sweep `for (numActiveThreads = GROUP_SIZE; numActiveThreads > 0; numActiveThreads /= 2)` com `GroupMemoryBarrierWithGroupSync()`, thread 0 salva o total em `GroupSums[group]` e zera `Temp[ITEMS_PER_GROUP-1]`, down-sweep `for (numActiveThreads = 1; numActiveThreads <= GROUP_SIZE; numActiveThreads *= 2)`.

Host (`Scan.cs`) é recursivo:
```csharp
int numGroups = Mathf.CeilToInt(elements.count / 2f / threadsPerGroup);
...
if (numGroups > 1)
{
    // Recursively calculate scan groupSums
    Run(groupSumBuffer);
    ...
    cs.Dispatch(combineKernel, numGroups, 1, 1);

```
Com N = 4096 partículas ⇒ numGroups = 8 ⇒ 1 nível de recursão ⇒ 3 dispatches de scan. Com N = 410k ⇒ ~2–3 níveis.

**Custo mobile**: `groupshared uint[512]` = 2 KB por grupo, e o up/down-sweep tem $2\log_2 512 = 18$ barreiras `GroupMemoryBarrierWithGroupSync`. Em Mali isso é o gargalo típico. `[INFERÊNCIA]`

### 3.5 Offsets (`SpatialOffsets.compute`, arquivo inteiro)

```hlsl
#pragma kernel InitializeOffsets
#pragma kernel CalculateOffsets

// Calculate offsets for the given sorted keys. For example, given:
// SortedKeys = {2, 2, 2, 3, 6, 6, 9, 9, 9, 9}
// Output will be ('x' represents irrelevant entries):
// Offsets = {x, x, 0, 3, x, x, 4, x, x, 6} 
// Now, to look up where the '6' keys start for instance, Offsets[6] gives the answer (4)

// NOTE: offsets buffer must be initialized with values equal to (or greater than) its length to ensure that this works correctly
StructuredBuffer<uint> SortedKeys;
RWStructuredBuffer<uint> Offsets;
uint numInputs;

[numthreads(256, 1, 1)]
void InitializeOffsets(uint3 id : SV_DispatchThreadID)
{
	if (id.x >= numInputs) { return; }
	Offsets[id.x] = numInputs;
}

[numthreads(256, 1, 1)]
void CalculateOffsets(uint3 id : SV_DispatchThreadID)
{
	if (id.x >= numInputs) { return; }

	uint i = id.x;
	uint null = numInputs;

	uint key = SortedKeys[i];
	uint keyPrev = i == 0 ? null : SortedKeys[i - 1];

	if (key != keyPrev)
	{
		Offsets[key] = i;
	}
}
```

O valor sentinela é `numInputs` (= N), o que explica a condição de parada dos loops de vizinhança: `while (currIndex < numParticles)` — bin vazio ⇒ `SpatialOffsets[key] == N` ⇒ loop nem entra. **Elegante: um único teste serve de "bin vazio" e de "fim do buffer".**

`SpatialHash.Run()` chama `spatialOffsetsCalc.Run(true, ...)` ⇒ o `InitializeOffsets` roda **sempre**, todo sub-step. `[INFERÊNCIA]` Isso é 1 dispatch de N threads desnecessário se você usar grade uniforme com contagem exata.

### 3.6 Reorder (por que existe)

```hlsl
[numthreads(NumThreads,1,1)]
void Reorder (uint3 id : SV_DispatchThreadID)
{
	if (id.x >= numParticles) return;

	uint sortedIndex = SortedIndices[id.x];
	SortTarget_Positions[id.x] = Positions[sortedIndex];
	SortTarget_PredictedPositions[id.x] = PredictedPositions[sortedIndex];
	SortTarget_Velocities[id.x] = Velocities[sortedIndex];
}

[numthreads(NumThreads,1,1)]
void ReorderCopyback (uint3 id : SV_DispatchThreadID)
{
	if (id.x >= numParticles) return;
	
	Positions[id.x] = SortTarget_Positions[id.x];
	PredictedPositions[id.x] = SortTarget_PredictedPositions[id.x];
	Velocities[id.x] = SortTarget_Velocities[id.x];
}
```

Troca uma indireção por acesso sequencial: depois do reorder, todas as partículas de um bin são **contíguas em memória**, então os 3 kernels de vizinhança leem linearmente. `[INFERÊNCIA]` Em mobile o ganho de coalescência costuma superar o custo dos 2 dispatches extras — mas o padrão de "copiar de volta" (2 passes) pode ser trocado por **ping-pong de buffers** (alterna `Positions`/`SortTarget_Positions` no host a cada frame), eliminando 1 dispatch de N e N leituras+escritas de 24 B.

## 4. Colisões, fronteiras, mouse e parâmetros do inspector

### 4.1 Colisões 2D (bounds + obstáculo retangular)

```hlsl
void HandleCollisions(uint particleIndex)
{
	float2 pos = Positions[particleIndex];
	float2 vel = Velocities[particleIndex];

	// Keep particle inside bounds
	const float2 halfSize = boundsSize * 0.5;
	float2 edgeDst = halfSize - abs(pos);

	if (edgeDst.x <= 0)
	{
		pos.x = halfSize.x * sign(pos.x);
		vel.x *= -1 * collisionDamping;
	}
	if (edgeDst.y <= 0)
	{
		pos.y = halfSize.y * sign(pos.y);
		vel.y *= -1 * collisionDamping;
	}

	// Collide particle against the test obstacle
	const float2 obstacleHalfSize = obstacleSize * 0.5;
	float2 obstacleEdgeDst = obstacleHalfSize - abs(pos - obstacleCentre);

	if (obstacleEdgeDst.x >= 0 && obstacleEdgeDst.y >= 0)
	{
		if (obstacleEdgeDst.x < obstacleEdgeDst.y) {
			pos.x = obstacleHalfSize.x * sign(pos.x - obstacleCentre.x) + obstacleCentre.x;
			vel.x *= -1 * collisionDamping;
		}
		else {
			pos.y = obstacleHalfSize.y * sign(pos.y - obstacleCentre.y) + obstacleCentre.y;
			vel.y *= -1 * collisionDamping;
		}
	}

	// Update position and velocity
	Positions[particleIndex] = pos;
	Velocities[particleIndex] = vel;
}
```

Características: projeção dura (snap) na borda + reflexão amortecida. O domínio é **centrado na origem** (`boundsSize` é o tamanho total, `halfSize = boundsSize*0.5`, sem offset de centro). O obstáculo empurra pelo **eixo de menor penetração**.

### 4.2 Colisões 3D (com transform arbitrário)

```hlsl
void ResolveCollisions(inout float3 pos, inout float3 vel, float collisionDamping)
{
    // Transform position/velocity to the local space of the bounding box
    float3 posLocal = mul(worldToLocal, float4(pos, 1)).xyz;
    float3 velocityLocal = mul(worldToLocal, float4(vel, 0)).xyz;

    // Calculate distance from box on each axis (negative values are outside box)
    const float3 halfSize = 0.5;
    const float3 edgeDst = halfSize - abs(posLocal);
    ...
    // Transform resolved position/velocity back to world space
    pos = mul(localToWorld, float4(posLocal, 1)).xyz;
    vel = mul(localToWorld, float4(velocityLocal, 0)).xyz;
}
```

O 3D trabalha em caixa unitária local (`halfSize = 0.5`) e usa `transform.localScale`/`localToWorldMatrix` como bounds — permite rotacionar/escalar o container. Custo: 4 mat-vec por partícula por sub-step.

```csharp
static Vector2Int CalculateSpawnCountPerAxisBox2D(Vector2 size, float spawnDensity)
{
    float area = size.x * size.y;
    int targetTotal = Mathf.CeilToInt(area * spawnDensity);

    float lenSum = size.x + size.y;

}
```

### 5.3 Como fazer metaball barato no seu jogo (recomendação)

`[INFERÊNCIA]` — plano concreto para o "caldo" da onda, estilo serigrafia:

1. **Render off-screen em 1/4 de resolução**, formato `R8` (ou `R16_SFloat` se quiser mais banda dinâmica). Um único `RenderTexture`, 270×600 em 1080p.
2. Desenhe as partículas como **quads aditivos** com um kernel radial barato — não precisa de `fwidth`, use LUT ou `saturate(1-sqrDst)²`:
   `Blend One One`, `ZWrite Off`, `ZTest Always`. Isso soma o "campo de influência".
3. **Threshold no composite** (full-screen blit ou material do URP Renderer Feature): `step(threshold, field)` → silhueta de metaball chapada. Um segundo `step(threshold2, field)` com `threshold2 > threshold` te dá o **contorno grosso preto** que a sua estética pede, de graça.
4. Aplique a textura de grão/halftone nessa máscara. A estética de risografia **favorece** o resultado low-res: aliasing lê como serigrafia, não como bug.
5. Zero `SV_Depth`, zero `discard`, zero RT float32, 2 render targets no total, 1 draw indirect + 1 blit.

Custo estimado: o fill em 1/4 de res com 1.000 partículas de 24 px de diâmetro ≈ 450k fragments aditivos — trivial para qualquer Adreno 6xx/Mali-G52.

Para a skin "Papel de Pão": mesma máscara, mas o composite usa a cor de caneta azul e multiplica pela textura de papel pardo — o pipeline não muda.

## 7. O que é caro demais para celular — e a alternativa

Ordem de prioridade (maior impacto primeiro).

| # | Custo no repo | Por que dói em Adreno/Mali | Alternativa recomendada |
|---|---|---|---|
| 1 | **~42–51 dispatches/frame** (14–17 × 3 sub-steps) | Cada `Dispatch` em GLES3.1 custa barreira de memória + flush de pipeline. Drivers mobile têm overhead de ~50–150 µs por dispatch com barreira. 45 × 100 µs = 4.5 ms só de overhead. | `iterationsPerFrame = 1` (ou 2). **Fundir kernels**: `ExternalForces`+`UpdateSpatialHash` num só; `CalculateDensities`+`CalculatePressureForce`+`CalculateViscosity` num só kernel que calcula densidade em registradores... não dá (precisa da densidade do vizinho). Solução real: fundir `Reorder`+`ReorderCopyback` via ping-pong e fundir pressão+viscosidade (mesma varredura de 9 células, dois acumuladores). ⇒ **6–8 dispatches/sub-step**. |
| 2 | **Counting sort + prefix scan Blelloch recursivo** (5–8 dispatches, `groupshared[512]`, 18 barreiras, `InterlockedAdd` em SSBO) | Atomics contenciosos + shared memory + recursão no host. É metade do orçamento de frame. | **Grade uniforme, sem ordenação.** O domínio do TAPA BURACO é fechado e pequeno. Use `cellCount = ceil(W/h) * ceil(H/h)` (ex. 32×18 = 576 células) com **capacidade fixa por célula** (ex. `MAX_PER_CELL = 16`): um buffer `uint CellCounts[cellCount]` e `uint CellItems[cellCount*16]`. Kernel 1: `InterlockedAdd(CellCounts[c],1,slot); if (slot<16) CellItems[c*16+slot]=i;`. **Zero sort, zero scan, zero offsets, zero reorder** ⇒ elimina 8–11 dispatches por sub-step. Overflow: a partícula simplesmente não é vista por vizinhos naquele frame (visualmente imperceptível numa onda). |
| 3 | **410.758 partículas** (cena 3D) / ~4.5k (2D) | Banda de memória: 80 B/partícula × leituras repetidas × 9 células. | Para uma onda estourando em tela de celular: **512–1.500 partículas** bastam se você usar a renderização de metaball do §5.3 (o campo suaviza o baixo número). Teste 768 primeiro. |
| 4 | **`float2`/`float3` full precision + `%` por N não-potência-de-2** | Mali-G5x/G7x têm FP16 com 2× throughput; divisão inteira é emulada (dezenas de ciclos). | `half2` nas velocidades e densidades (posições mantenha `float` para não ter jitter espacial). Use `min16float`/`half` explícito no HLSL; em Unity, `#pragma use_dxc` + tipos `half`, ou empacote 2×`half` em 1 `uint` (`f32tof16`/`f16tof32`) reduzindo o buffer de velocidade de 8 B para 4 B. Com grade uniforme o `%` desaparece (índice de célula é direto). |
| 5 | **`SmoothingKernelPoly6` na viscosidade** | `(h²-d²)³` = 3 mults + a normalização `1/h⁸` amplifica erro em fp16. | Troque por `SpikyKernelPow2` (já calculado!) ou pelo `LinearKernel(dst,radius) = 1 - dst/radius` que existe em `FluidMaths3D.hlsl` e é 1 mad. Recalibre `viscosityStrength`. |
| 6 | **Pipeline screen-space 3D** (6 RTs, 3 em `R32G32B32A32_SFloat` full-res, 8 trocas de RT, bilateral 1D/2D) | ~124 MB de VRAM, e cada `SetRenderTarget` numa GPU tile-based força resolve+reload de todos os tiles. | Descartar inteiro. Usar §5.3: 1 RT `R8` em 1/4 de res + 1 blit de threshold. |
| 7 | **`Raymarching.shader`** (`numRefractions` loops × marcha por passo × `Texture3D`) e `UpdateDensityTexture` `[numthreads(8,8,8)]` avaliando SPH de 27 células por voxel | Loop dinâmico no fragment + Texture3D trilinear; e o preenchimento do volume é $O(\text{voxels}\times\text{vizinhos})$. | Descartar. Não há versão mobile viável disso. |
| 8 | **Marching Cubes** (`[numthreads(8,8,8)]`, LUT em `MarchingCubesLUT.txt`, append buffer + `RenderArgsCompute.compute`) | Append buffers + indirect args + geometria dinâmica por frame. | Descartar. Em 2D o equivalente barato é **marching squares na CPU** sobre uma grade 32×18 (576 células, ~0.1 ms em C# com `NativeArray`) gerando um `Mesh` de linha para o contorno serigráfico. |
| 9 | **`SV_Depth` + `discard`** no `ParticleDepth.shader` | Mata early-Z / hidden surface removal (FPK do Mali). | Não escrever depth nas partículas. Ordem de composição resolvida por additive blending (comutativo). |
| 10 | **`Blend SrcAlpha OneMinusSrcAlpha` + `ZWrite Off`** em full-res com sobreposição alta | Overdraw de blend é o gargalo #1 de fill em mobile. | Additive num RT de 1/4 de res (§5.3). Fill cai 16×. |
| 11 | **`InitializeOffsets` rodando todo sub-step** (`spatialOffsetsCalc.Run(true, ...)`) | N threads de escrita pura, 3× por frame, sem necessidade. | Com grade uniforme: só `CellCounts` precisa ser zerado — 576 entradas em vez de N. |
| 12 | `Camera.main` em `UpdateSettings()` **e** em `OnDrawGizmos()` (busca por tag toda chamada) | Alocação/busca gerenciada por frame. | Cachear a `Camera` num campo. |
| 13 | `Graphics.DrawMeshInstancedIndirect` exige indirect draw (GLES 3.1+AEP / ES3.2 / Vulkan) | Alguns Adreno 5xx antigos com ES3.1 puro reprovam. | `[INFERÊNCIA]` Checar `SystemInfo.supportsIndirectArgumentsBuffer` e `SystemInfo.supportsComputeShaders`; fallback: `Graphics.RenderPrimitives`/`DrawProcedural` com contagem fixa (você sabe N em compile time) — dispensa args buffer. Force **Vulkan** como primeiro Graphics API no Player Settings Android. |

### 7.1 Orçamento-alvo sugerido (`[INFERÊNCIA]`)

Para 60 fps num celular mediano (orçamento total ~16.6 ms, dos quais ~4 ms para o fluido):

| Parâmetro | Repo (2D) | Alvo mobile |
|---|---|---|
| Partículas | ~4.500 | **768** |
| `iterationsPerFrame` | 3 | **1** |
| Dispatches/frame | ~45 | **≤ 6** |
| Vizinhança | hash + sort + offsets | grade uniforme 32×18, `MAX_PER_CELL=16` |
| numthreads | 64 | **64** (bom: múltiplo de 64 = wavefront Adreno e warp Mali) |
| Precisão | float32 | posições float32, velocidade/densidade half |
| RT de render | backbuffer full-res, alpha blend | `R8` em 1/4 res, additive + threshold |
| Bytes/partícula | 80 | ~20 (pos 8 + vel 4 + dens 4 + célula 4) |

Sobre `numthreads`: **64 é a escolha certa** para mobile (é exatamente o que o 2D usa). Adreno tem wavefront de 64 (ou 128), Mali-Gxx usa warp de 4/8/16 mas 64 divide bem; `256` (usado no 3D e no sort) desperdiça ocupação quando N é pequeno — com 768 partículas, `256` dá só 3 grupos, insuficiente para saturar os shader cores.

### 7.2 Calibração após reduzir partículas

Ao cair de 4.500 para 768 partículas na mesma área, a densidade em repouso cai. Sequência de recalibração `[INFERÊNCIA]`:
1. Escolha `smoothingRadius` ≈ 2.5–3× o espaçamento médio entre partículas (no repo: espaçamento ≈ $1/\sqrt{159}$ ≈ 0.079, `h` = 0.35 ⇒ **4.4×**, ~60 vizinhos).
2. Rode 1 frame com `pressureMultiplier = 0` e o fluido em grade regular; leia `Densities[i].x` (via `AsyncGPUReadback` num script de editor) — esse é seu `targetDensity`.
3. `pressureMultiplier`: comece em `500 * (h_novo/0.35)²`; aumente até o fluido parar de comprimir, pare antes de vibrar.
4. `nearPressureMultiplier` ≈ 1–4% de `pressureMultiplier` (Test A: 5/500 = 1%; Test B: 18/225 = 8%).
5. Condição de estabilidade (CFL): $\Delta t < \dfrac{0.4\,h}{v_{\max}}$. Com `h=0.35` e `v_max=10` ⇒ $\Delta t < 14$ ms. Com 1 sub-step a 60 fps (`Δt = 16.7 ms`) você está **na margem** — por isso o clamp `maxTimestepFPS` e, se necessário, 2 sub-steps.

### 7.3 Alternativa radical: não usar SPH

`[INFERÊNCIA]` Para o efeito "leva um caldo — onda estoura na tela", que é **um evento único, não-interativo, de ~1.5 s**, SPH é sobre-engenharia. Duas alternativas com 1–2% do custo:

- **Shallow water 1D / heightfield**: um array de 128 alturas + velocidades, integração explícita `h'' = c²∇²h`, rasterizado como uma faixa de mesh com contorno grosso. Roda na CPU em <0.05 ms. É como a maioria dos jogos 2D faz água.
- **Animação pré-autorada** (spritesheet serigráfico ou mesh animado por shader) + ~100 partículas de spray com `VFX Graph`/`ParticleSystem` clássico. Zero compute shader, zero risco de compatibilidade, e permite controle artístico total do look risografia — que é justamente o seu diferencial.

Use SPH **só** se o fluido precisar ser interativo (ex.: o jogador desenha na areia e a água responde). Se o caldo é só feedback de derrota, o custo/benefício não fecha.

## 8. Checklist de reimplementação (sem reabrir o repo)

**Buffers (2D, grade uniforme, mobile):**
```
Positions          : RWStructuredBuffer<float2>  [N]
Velocities         : RWStructuredBuffer<float2>  [N]   (ou uint empacotado half2)
PredictedPositions : RWStructuredBuffer<float2>  [N]
Densities          : RWStructuredBuffer<float2>  [N]   (x=ρ, y=ρ_near)
CellCounts         : RWStructuredBuffer<uint>    [cellsX*cellsY]
CellItems          : RWStructuredBuffer<uint>    [cellsX*cellsY*MAX_PER_CELL]
```

**Uniforms:** `numParticles, gravity, deltaTime, collisionDamping, smoothingRadius, targetDensity, pressureMultiplier, nearPressureMultiplier, viscosityStrength, boundsSize, interactionInputPoint, interactionInputStrength, interactionInputRadius` + 5 fatores de escala (ou 3 se cortar Poly6).

**Constantes 2D (h = smoothingRadius):**
```
SpikyPow2ScalingFactor            = 6  / (π·h⁴)
SpikyPow3ScalingFactor            = 10 / (π·h⁵)
SpikyPow2DerivativeScalingFactor  = 12 / (π·h⁴)
SpikyPow3DerivativeScalingFactor  = 30 / (π·h⁵)
Poly6ScalingFactor                = 4  / (π·h⁸)
```

**Ordem dos kernels (alvo, 6 dispatches/sub-step):**
1. `ExternalForcesAndPredict` — gravidade + interação, `PredictedPositions = Positions + Velocities/120`
2. `ClearCells` — zera `CellCounts` (cellCount threads, não N)
3. `FillCells` — `InterlockedAdd` na célula de `PredictedPositions`
4. `CalculateDensities` — 9 células, Spiky² e Spiky³, inclui self
5. `PressureAndViscosity` — 9 células, exclui self, dois acumuladores, `v += (a_P + ν·Δv)·Δt`
6. `UpdatePositions` — `x += v·Δt`, colisão AABB com snap + `v *= -damping`

**Equações:**
$$P_i = k(\rho_i-\rho_0),\quad P^{near}_i = k_{near}\rho^{near}_i$$
$$\mathbf a_i = \frac{1}{\rho_i}\sum_{j\ne i}\hat{\mathbf r}_{ij}\Big[\tfrac{\bar P_{ij}W'_{S2}}{\rho_j}+\tfrac{\bar P^{near}_{ij}W'_{S3}}{\rho^{near}_j}\Big] \qquad \mathbf a^{visc}_i = \nu\sum_{j\ne i}(\mathbf v_j-\mathbf v_i)W$$

**Render:** `Graphics.RenderPrimitives`/`DrawMeshInstancedIndirect` de quads aditivos num RT `R8` a 1/4 de res → blit com dois `step()` (preenchimento + contorno) → grão/halftone.
